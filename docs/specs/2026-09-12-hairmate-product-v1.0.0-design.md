- 决策标识：**已确认**为对话中达成的产品决定；**推荐基线**为待技术验证的实现建议；**开放决策**说明决定条件及边界，不作为已批准功能。

## 产品摘要

原始描述：

> A mate that helps you complete the entire process from hairstyle recommendations and selection, to scene simulation, and finally to offline haircuts.

中文定位：HairMate 是一位帮助用户理解自身条件、探索并选择发型、预览效果、与理发师沟通及复盘真实结果的个人发型顾问。

核心价值不是生成一张好看的换发型图片，而是降低“选不明白、说不清楚、实际效果不确定”的试错成本。V1 不承诺已经解决理发师能力识别问题；通过具体理发历程积累数据，为后续匹配理发师提供基础。

已确认的主路径：

**真实照片与需求 → 可解释推荐 → 基准发型模拟 → 选定方案及 Haircut Brief → 用户自行选择理发师、现场确认并理发 → 剪后及首次自行打理后的反馈。**

客户端采用 **Expo + React Native + TypeScript + Expo Router，App 优先**。首先通过真实设备和小范围内测验证闭环；Web 是未来按需增加的入口，不是必须经过的前置阶段。

首批服务地区已确认以中国大陆为主。技术推荐据此收敛为国内部署、国内模型接口、私有图片存储和自托管认证；具体服务组合与模型效果仍需验证，不等于已经批准采购。

## 1. 目标用户与核心问题

### 可选方案与结论

| 方案 | 重点解决的问题 | 取舍 |
| --- | --- | --- |
| A．高形象要求、缺少可靠发型判断依据的用户（已确认） | 不知道什么适合自己，也不确定如何在线下实现 | 需要连接选型、沟通和真实结果，最贴近当前用户需求 |
| B．已有明确参考图、主要缺少沟通方法的用户 | 把想要的效果传达给理发师 | 更容易收敛，但不能充分解决“不知道选什么” |
| C．为重要活动准备形象的用户 | 面试、约会或正式活动前的集中决策 | 动机明确，但不能默认代表日常持续需求 |

### 已确认的目标与问题

首批目标用户：对个人形象有较高要求，缺乏判断发型是否适合自己的可靠方法，并难以找到能落实方案的理发师的人。

当前直接证据来自发起人自身经历：网络推荐散乱且难理解；理发师水平不一，个性化设计能力难判断；理发试错成本高，头发恢复和下一次尝试的周期长。这是初始用户证据，不是已经验证的市场规模或普遍性结论。

需要分别处理三类不确定性：

1. **选择不确定性**：什么适合我，理由是什么，候选之间如何取舍？
2. **执行不确定性**：理发师是否理解目标、是否具备条件落实？
3. **结果不确定性**：离店后、自己洗头打理后，是否仍符合预期？

不预设用户性别、年龄、发长或仅接受小幅调整；也不把低维护成本设为所有人的首要目标。先识别用户愿意为审美效果投入什么，再做取舍。

研究方法建议：围绕用户最近一次真实理发经历访谈、观察实际使用和回访，检验需求假设，而不是仅询问是否喜欢概念。参考 [GOV.UK：从用户需求开始研究](https://www.gov.uk/service-manual/user-research/start-by-learning-user-needs)。

## 2. MVP 的产品闭环做到哪里

### 可选方案与结论

| 方案 | 起点与终点 | 取舍 |
| --- | --- | --- |
| A．完成一次真实理发并复盘（已确认） | 创建本次理发计划 → 首次自行洗头／打理后的反馈 | 能检验线下价值，但需要跨天跟进 |
| B．完成线上方案交付 | 提供需求 → 导出 Brief | 验证更快，但不知道真实结果是否改善 |
| C．同时完成可信理发师匹配 | 提供需求 → 匹配执行者 → 理发与复盘 | 更完整地解决盲选，但需要可靠供给与历史证据，后续考虑 |

### V1 必须连通的环节

用户主动创建一次 HairJourney，提供照片和目标，确认影响推荐的关键条件；获得候选及解释，通过基准模拟辅助判断，选定具体方案版本并取得 Brief；自行找理发师，出示 Brief，记录现场确认或调整；理发后记录效果，并在首次自行洗头／打理后再次反馈。

V1 不需要替用户预约、支付或联系理发师。用户是否实际出示 Brief、是否真实理发和如何打理，允许本人记录，需标明信息来源。

为未来理发师匹配保留：个人头发条件、目标方案、现场修改、实际执行者及门店、剪后和打理体验。不能仅用门店评分代替个人能力，也不能凭少量、未经核实的自报记录直接形成能力排名。

## 3. Agent 与传统程序的职责边界

### 可选方案与结论

| 方案 | 组织方式 | 取舍 |
| --- | --- | --- |
| A．明确业务流程 + 单一顾问 Agent（已确认） | 程序控制流程，Agent 处理需要理解和判断的步骤 | 保留个性化能力，权限和状态可测试 |
| B．表单／规则 + 局部 AI 功能 | 预定义问题与规则，AI 只完成局部解释或生成 | 更容易控制，但难处理模糊偏好和个体取舍 |
| C．多个专职 Agent 协作 | 推荐、模拟、Brief、复盘各设 Agent | 协调、排错和成本上升，V1 不引入 |

### 已确认的责任分配

| 任务 | Agent | 确定性程序／数据库／API |
| --- | --- | --- |
| 理解需求 | 理解自然语言，发现缺失信息，提出追问 | 保存原始输入、来源及确认状态 |
| 推荐 | 比较候选，解释效果、限制与维护取舍 | 检索数据，校验结构与已确认硬约束，保留依据版本 |
| 模拟 | 根据选定方案起草图片编辑要求 | 检查授权，调用图像模型，管理任务、额度和结果 |
| 方案与 Brief | 起草分区要求、风险和现场核实事项 | 关联版本，记录用户确认，展示及导出 |
| 复盘 | 整理目标与实际差异，提出调整建议 | 保存多时间点记录，不擅自覆盖长期档案 |
| 权限与状态 | 只能提出允许范围内的动作 | 最终执行访问控制、状态转换、参数校验和费用上限 |

图像模型本身是非确定性的生成系统；确定性的是调用条件、状态管理和校验机制，不能将“通过 API 调用”理解为“输出必然正确”。

三条事实边界：照片推测不等于已确认条件；模拟图不等于现实可实现的保证；一次不满意不等于用户的永久偏好或理发师的稳定能力结论。

业务流程与 Agent 的区分参考 [Anthropic：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)。本产品采用明确流程并限制 Agent 工具权限，而非让模型自行控制全部业务。

## 4. Agent 应拥有多大的自主权

### 可选方案与结论

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A．授权范围内自动推进，关键决定由用户确认（已确认） | 授权目的、范围和额度后，自动完成内部步骤 | 减少打断，同时保留用户控制 |
| B．每阶段都确认 | 推荐、每次生成、每次修改分别审批 | 容易理解，但交互负担较大 |
| C．预授权整批准备 | 一次授权多套候选、模拟及材料准备 | 适合需求稳定的后续用户，额度与范围更难把握 |

### 已确认的授权规则

- 自动执行：既有授权内的理解、检索、候选比较、草稿准备、模拟与有限重试、保存本次反馈和复盘建议。
- 用户决定：关键头发条件与硬限制、最终方案和 Brief、模拟范围和追加额度、现场理发变更、对外分享内容与对象。
- 已给定的明确授权在其范围内持续有效，不要求用户逐次确认内部工具调用；扩大范围、新增接收方或增加额度时重新确认。
- 用户主动表达“以后都按这个偏好记住”可以记录为长期偏好；模型从单次行为推测出的偏好，需要确认后才能成为长期事实。
- 上传用于个人咨询和模拟，不等于同意公开照片、用于其他用户的匹配分析或发送给理发师。照片处理用途与对外分享分别管理。

服务端执行确认检查和额度约束，不能仅依赖提示词。模型即使提出越权动作，也不得绕过这些检查。

## 5. 发型推荐的核心依据

### 可选方案与结论

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A．实际条件约束 + 审美探索（已确认） | 先理解可行条件与投入意愿，再探索风格 | 个性化和可解释性较好，需要逐步补齐信息 |
| B．视觉偏好优先 | 从用户喜欢／不喜欢的参考图出发 | 降低表达难度，但必须补上现实条件核实 |
| C．结构化发型资料库优先 | 从有来源、带条件标签的模板筛选 | 便于追溯和校验，但初期覆盖可能有限 |

以 A 为主，结合 B 的参考图沟通和 C 的有来源资料；不依赖模型无依据地给发型贴结论。

### 输入与信息质量

| 维度 | 需要理解的内容 | 信息边界 |
| --- | --- | --- |
| 头发条件 | 当前长度、自然直卷、粗细软硬、密度、走向、难处理区域、烫染经历 | 区分照片可见观察、用户自述与现场核实；不把不可见条件当已知 |
| 外观与目标 | 可见比例、用户希望突出／保留／改变的部分 | 脸型不是唯一依据，不进行未经验证的颜值评分 |
| 审美偏好 | 喜欢／排斥的风格、参考图中的具体细节、过去经验 | 区分喜欢图片整体氛围与喜欢其中的发型结构 |
| 维护投入 | 每日时间、工具与技能、预算、修剪频率、烫染接受度 | 由用户决定审美收益与维护投入的取舍 |
| 生活条件 | 工作、活动、运动，以及相关的眼镜／帽子使用等 | 仅在影响选择时收集，不默认推断职业或生活方式 |

渐进收集信息：先获得足以形成有用候选的输入，再追问决定可行性或排序的未知条件，避免一次性长问卷。基础头发条件的咨询维度可参考 [AQA：Hair consultation 单元](https://www.aqa.org.uk/programmes/unit-award-scheme/unit-details?unit=90166)，但不将模型观察视为专业现场诊断。

### 每个候选必须解释

1. 对应哪些已知条件与偏好，依据来自哪里。
2. 主要改变、保留内容，以及与其他候选的区别。
3. 日常打理与周期维护要求，哪些效果依赖工具、技巧或现场条件。
4. 哪些条件符合、冲突或待确认；存在关键冲突时不作为可直接执行方案。

不输出未经校准的“96% 适合度”。评价分为：依据真实与硬约束遵守、解释是否帮助选择、现场是否需要大幅改案、剪后喜好及自行打理体验。最终评价不能只看用户是否喜欢模拟图。

## 6. 核心数据模型

### 可选方案与结论

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A．结构化核心实体 + 关键版本快照（已确认） | 以一次 HairJourney 关联决策与真实结果 | 支持复盘、追溯和未来匹配，复杂度可控 |
| B．单份咨询文档／聊天记录 | 一次咨询全部放在一个文档 | 启动简单，但版本、查询和结果关联困难 |
| C．完整事件溯源／知识图谱 | 每次变化建事件，并构建复杂关系网络 | 适合未来复杂分析，V1 不引入 |

### 概念实体

| 实体 | 职责及关键关联 |
| --- | --- |
| User | 身份、数据所有权、授权与同意记录 |
| HairProfile | 当前头发条件与偏好；每项的信息来源、更新时间、确认状态；供历程引用的快照 |
| HairJourney | 一次理发目标、进行状态、选定方案以及从咨询到回访的主线 |
| Hairstyle | 可复用、有来源的通用发型资料；不是用户最终个性化方案 |
| StylePlan | 针对用户的候选／选定方案、硬约束、分区效果、维护要求与版本 |
| Recommendation | 一轮推荐及理由，引用使用的档案快照与候选方案版本 |
| Simulation | 输入素材、明确的方案版本、模拟类型、任务状态与输出素材 |
| HaircutBrief | 具体方案版本的交付要求、参考素材、用户确认及交付版本 |
| HaircutVisit | 实际理发日期、当时的理发师和门店、原 Brief、现场约定及实际执行记录 |
| Feedback | 剪后和首次自行打理等多时点反馈；分别记录选择、沟通、效果与维护体验 |
| Stylist | 具体个人；允许未知、昵称或自报，保留信息来源和核验状态 |
| Salon | 具体门店；与 Stylist 区分，允许理发师换店 |
| MediaAsset | 原照、参考图、模拟图与剪后图；记录来源、所有权、用途、访问及删除状态 |

这些是业务对象，不强制每个对象对应一张数据库表。关系与外键约束有助于防止悬空引用，参考 [PostgreSQL：约束](https://www.postgresql.org/docs/18/ddl-constraints.html)。

### 版本、事实与生命周期规则

- 更新当前 HairProfile 不覆盖历史推荐所用的档案快照。
- StylePlan 修改产生新版本；Simulation 和 Brief 始终引用具体版本。旧材料标为旧版，不能悄悄作为新方案的效果展示。
- 原计划、用户记录的现场约定、实际结果分别保存；实际没有执行某项要求，不应修改历史 Brief 来掩盖差异。
- HaircutVisit 保留理发当时的个人与门店关系；同名理发师不自动合并，门店评分不当作个人能力。
- 自报、用户代录和独立核验的信息分别标记；未知字段允许为空，不用模型猜测填满。
- 个人反馈默认用于本人复盘；公开展示或跨用户分析另行明确用途与授权。
- 用户可删除图片，关联材料显示素材已不可用；结构化记录按用户选择保留或删除。删除历程／账号应处理关联数据，不能以“历史快照”为理由无限保留已请求删除的内容。
- 备份保留期、删除生效窗口及恢复后重新执行删除的机制，需要在所选存储方案落地时定义，并向用户说明；不能宣称删除主库就等于备份中即时消失。

## 7. “场景模拟”的产品定义

### 可选方案与结论

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A．基准对比 + 真实生活照片模拟方向（按用户修正确认） | 先验证同条件发型对比；生活照片功能另行细化 | 保持可比较性，同时保留用户关心的真实生活效果 |
| B．只提供基准照片对比 | 在同一输入照片上比较候选 | 范围最小，但缺少生活环境中的判断材料 |
| C．完整多角度与复杂场景体系 | 多角度一致性、丰富变换与交互 | 技术和验收难度更高，不是 V1 基线 |

### V1 必须实现：基准发型模拟

- 以用户真实照片为底图，在相同主要角度和非发型条件下展示候选，支持与原图比较。
- 保持人物身份及面部特征、服装、背景等非目标内容；不得通过美颜、瘦脸或改变五官使候选显得更好。
- 输入关联选定的候选版本，并经用户确认本次模拟范围与额度。V1 不要求为所有候选自动生成大量图片。
- 以一个主要真实角度为基线；补充侧面／后面照片可用于理解条件，但不承诺完整多角度重建、3D 或实时 AR。
- 明确标注为效果示意，而非长度测量或现实可实现性的保证。

有效结果需要同时满足：人物身份没有明显漂移、主要发型要求一致、非发型要素没有影响比较的明显变化、输入和方案版本可追溯。小规模试点通过人工检查验证这些条件，不能只以生成接口返回成功作为合格标准。

### 用户明确保留的开放决策：真实生活照片模拟

已确认方向是：**用户提供本来就处于具体生活场景中的本人照片，Agent 通过提示词模板，在该照片上应用选定发型。**

不是根据“工作、约会、正式活动”等文字重新生成背景、服装和场景。应保留底图的真实生活环境与非发型要素。

照片输入要求、支持范围、提示词模板与交互、额度、质量标准仍需用户参与细化。在这些条件确定之前，不纳入 V1 强制 Golden Path，也不预先宣告永久排除或自动延期。后续如纳入某次发布，需单独明确规格和验收，不以本节方向代替批准。

### 失败处理

不合格图片明确标为失败，不作为选定方案的有效模拟依据；允许在已授权范围内有限重试、补充或更换照片，也允许用户跳过模拟继续咨询或导出文字材料。没有有效基准模拟的经历单列为降级路径，不计完整 Golden Path。

## 8. 从线上推荐到线下理发：Haircut Brief

### 可选方案与结论

| 方案 | 交付形式 | 取舍 |
| --- | --- | --- |
| A．简明摘要 + 分区细节 + 选定参考图（已确认） | 手机快速浏览，按需展开细节并导出 | 兼顾现场效率和信息完整性 |
| B．参考图 + 少量标注 | 主要用图片表达保留／修改部位 | 直观，但难覆盖隐藏条件和维护限制 |
| C．完整咨询记录 | 将聊天历史交给理发师 | 可作补充，但信息噪声大，不作为主交付 |

### 必须包含的结构化内容

| 分组 | 内容与要求 |
| --- | --- |
| 方案身份 | 本次目标、选定 StylePlan 版本、确认日期；旧版明确标识 |
| 必须保留／不可突破 | 最短可接受范围、不希望改变的部位、不接受的烫染或其他处理 |
| 整体效果 | 轮廓、体积、层次、纹理，期待的主要变化 |
| 分区要求 | 顶部、刘海、两侧、鬓角、后区分别描述目标；未知或不适用明确标注 |
| 长度表达 | 使用部位参照、合理范围或现场确认的实测值；区分干发／造型后等影响表达的条件 |
| 烫染 | 是否接受、希望达到的效果与限制；可行性和实际操作由专业人员现场确认 |
| 图片依据 | 用户选定的原照、参考图、模拟图；标明每张图用于参考哪一部分 |
| 维护要求 | 可接受的时间、工具、造型步骤和修剪频率；明确效果依赖的条件 |
| 现场核实 | 无法从照片确认的头发条件、可能需要调整的部分及需用户再次决定的事项 |

Agent 不凭照片编造精确厘米数、剪切角度或化学处理配方。不确定时写清目标和待核实项，而不是给出看似专业的虚假精度。现场检查、协商结果和服务记录的重要性可参考 [英国职业标准：Cut and clipper hair](https://www.ukstandards.org.uk/en/nos-finder/SKAHDBR3/cut-and-clipper-hair-)。

### 现场闭环

用户出示 Brief → 理发师核实条件并提出建议 → 用户接受／拒绝调整并记录 → 理发 → 对照原目标、现场约定和实际结果复盘。

理发师无需注册 HairMate。用户代录意见标记为“用户记录的现场沟通”，不冒充理发师本人在线确认。Brief 改善沟通，不证明理发师有相应能力，也不保证实际效果。

手机查看与保存／导出是 V1 能力；具体文件格式在交互设计时选择，应验证接收方无需 HairMate 账号也能读懂用户主动出示的材料。导出后的外部副本不能承诺远程撤回。

## 9. MVP 明确不做什么

### 可选做法与结论

| 做法 | 边界 | 取舍 |
| --- | --- | --- |
| A．以真实理发闭环界定 V1（已确认） | 每个功能必须服务选型、交付或复盘 | 能控制范围并验证最终价值 |
| B．分模块试验，再整合验收 | 先分别验证推荐、模拟、Brief 等风险 | 可作为验证方法，但单模块通过不等于 V1 完成 |
| C．首发覆盖平台型服务 | 加入匹配、交易、商家、社区 | 扩大供给和运营依赖，V1 排除 |

### V1 范围

**必须包含：**档案与历程、单一顾问咨询、可解释推荐、同条件基准模拟、方案确认与 Brief、线下记录、剪后及自行打理反馈；配套的权限、删除、版本、额度和失败恢复。

**明确不包含：**

- 理发师自动匹配、推荐、排名或能力认证。
- 预约、在线支付、订单交易与代办。
- 商家后台、理发师入驻管理。
- 与理发师即时聊天、自动联系理发师。
- 社区、公开晒图、点赞关注、信息流。
- 实时 AR、视频试戴、完整多角度重建。
- 根据文字生成新生活场景，以及妆容、穿搭推荐。
- 多 Agent 协作架构。

手动记录理发师和门店、可选日期／实际费用、用户自行查看和导出材料，不等于引入交易平台。真实生活照片模拟保持第 7 节的开放状态，不混入已排除功能。

## 10. 什么结果代表 HairMate V1 成功

### 可选验证方案与结论

| 方案 | 验证什么 | 取舍 |
| --- | --- | --- |
| A．完整历程验收 + 小规模真实试用（已确认） | 功能可用，真实用户是否获得具体帮助 | 能发现主要问题，但不证明普遍或长期效果 |
| B．与用户过去的方法比较 | 是否更容易选择、沟通和理解维护 | 可补充定性证据，注意记忆偏差与不可比条件 |
| C．跨多次理发持续观察 | 是否减少长期试错和提高稳定满意度 | 更接近长期目标，验证周期更长，后续开展 |

### Golden Path

| 步骤 | 用户动作 | 完成证据 |
| --- | --- | --- |
| 1 | 创建历程，提供照片与需求，确认关键条件 | 历程、可用照片、档案快照和确认记录 |
| 2 | 理解候选及取舍，选择模拟范围与额度 | 有依据的候选、明确授权和约束 |
| 3 | 查看至少一个有效基准模拟，并与原照比较 | 通过质量检查的输出、原图及方案版本关联、用户比较记录 |
| 4 | 选定具体方案版本，确认并取得 Brief | 已确认版本和可现场使用的交付材料 |
| 5 | 实际理发并出示 Brief，记录现场约定／调整和执行 | 实际理发记录；来源可为本人自报，未知执行者不强制猜填 |
| 6 | 记录剪后效果及首次自行洗头／打理后的体验 | 两个时间点的反馈，与本次历程关联 |

闭环允许跨天、跨会话完成。不满意但记录完整仍算完成；满意度独立衡量。模拟失败后跳过、仅导出 Brief、没有真实理发或缺少自行打理反馈，都不计完整 Golden Path。

### 技术与产品验收门槛

| 验收项 | 必须通过的检查 |
| --- | --- |
| 推荐依据 | 已确认硬限制不被静默忽略；关键未知显式保留或追问；理由可追溯到实际输入 |
| 模拟质量 | 试点人工检查身份、主要发型要求和非发型要素一致性；坏图可拒绝并有限恢复 |
| 版本一致性 | 修改方案后旧图和旧 Brief 不冒充新版；历史依据仍可查 |
| 授权与隔离 | 未授权读取、分享或追加生成被服务端阻止；导出只包含用户选择的材料 |
| 成本与恢复 | 达到额度停止；断网／关闭 App 后能恢复查看服务端任务；重复操作不重复创建同一业务任务 |
| 真实记录 | 原计划、现场调整和实际结果可区分；自报不显示为已独立核验 |
| 隐私操作 | 图片／历程删除按约定处理关联引用；日志不泄露原图、私密对话或访问凭据 |
| 跨会话使用 | 登录恢复、本次历程继续、现场查看及剪后回访可连通 |

技术验收通过、至少一名真实用户走完整条路径，才说明核心闭环已经跑通；这仍不等于市场价值已经得到充分验证。

### 首轮真实试用目标

1. 发起人先完成一次自己的真实理发，用于发现流程与沟通问题；不计入后续五人试点分母。
2. 邀请 **5 名**近期有理发计划、符合目标特征的用户；从每人创建历程起观察 **28 天**。
3. 至少 **3/5** 完成全部 Golden Path。
4. 完成者中至少 **2 人**能说明一个具体帮助，且首次自行打理后总体满意度达到 **4/5 分或以上**。帮助与满意两项均满足，才计入该价值指标。
5. 同时报告完整完成数／全部 5 人、满足价值条件数／全部 5 人、满足价值条件数／完成者。
6. 已进入这五人试点但放弃、失败、未理发、未出示 Brief 或未回访的人保留在分母，记录原因；超过各自观察窗口完成的结果另列，不悄悄改变首轮口径。

这些是双方约定的内部实验目标，不是行业基准或效果承诺。小规模研究适合发现问题和价值线索，不能据此声称已证明长期降低试错成本。参考 [GOV.UK：规划用户研究](https://www.gov.uk/service-manual/user-research/plan-user-research-for-your-service) 和 [完成率的统计口径](https://www.gov.uk/service-manual/measuring-success/measuring-completion-rate)。

## 11. 技术栈与 Web → App 路径

### 11.1 客户端路线：App 优先已确认

| 方案 | 路线 | 取舍 |
| --- | --- | --- |
| A．直接做跨平台 App（已确认） | Expo + React Native + TypeScript + Expo Router | 直接验证照片输入、现场使用和跨天回访；需要处理原生权限、构建及平台适配 |
| B．先移动 Web／PWA，再做 App | 先链接试用，再建设原生客户端 | 早期分发轻，但 Web 页面与导航不能视为可无成本迁移的原生界面 |
| C．Web + Capacitor 容器 | Web 主体结合原生插件与安装包 | 适合已有 Web 资产；仍需处理原生插件、权限、测试和发行 |

选择 A 的产品理由：HairMate 的核心发生在手机照片、现场出示材料和跨天回访中，而最终目标就是 App；当前没有需要优先保留的 Web 应用资产。接受 App 内测的分发成本，以直接验证目标使用环境。

Expo 提供 Android、iOS 和 Web 的统一项目基础，但各平台依然需要适配和测试。先用开发构建与内部发布验证真实设备，不把 Expo Go 中跑通等同于正式 App 就绪。参考 [Expo 项目与 TypeScript／Router](https://docs.expo.dev/tutorial/create-your-first-app/)、[开发构建](https://docs.expo.dev/develop/development-builds/introduction/)、[内部分发](https://docs.expo.dev/build/internal-distribution/)；容器方案参考 [Capacitor 官方文档](https://capacitorjs.com/docs)。

首批内测设备是 iOS、Android 还是两者尚未决定；不因跨平台技术而自动承诺双端同期完成全部发行工作。

### 11.2 推荐技术基线与选择状态

除已经确认的客户端和产品边界外，下表是技术推荐基线，不代表已经开通、购买或验证具体服务。

| 层 | V1 推荐做法 | 状态／选择条件 |
| --- | --- | --- |
| 客户端 | Expo、React Native、TypeScript、Expo Router | App 优先方向已确认；具体依赖版本在初始化时锁定 |
| 后端 | 独立 TypeScript API，Fastify 初选，模块化单体 | 推荐基线；不把业务后端绑定到 Web 页面服务 |
| Agent 运行层 | 单一顾问；AI SDK + 国内 Provider 适配初选 | 直连选定百炼地域，不把海外 AI Gateway 作为必需依赖；校验实际支持能力 |
| 图片任务 | 独立 Node.js worker，持久化任务状态与有限重试 | 推荐基线；与 API 可同仓，但独立进程运行 |
| 数据库 | 阿里云 RDS PostgreSQL 初选；结构化关系 + 必要的 JSONB；版本迁移 | 推荐基线；不把全部业务状态仅藏在聊天记录中 |
| 队列 | pg-boss + PostgreSQL | 推荐基线；核实数据库版本和建表权限，不额外引入 Redis |
| 认证 | Better Auth 自托管 + Expo 集成；内测登录方式初选邮箱／密码 | 推荐基线；验证会话恢复、邮件投递与找回；手机号／第三方登录按需求再定 |
| 图片存储 | 阿里云 OSS 私有 Bucket、短时授权、素材生命周期 | 推荐基线；不为方便模型读取而将用户照片设为公开 |
| 地图／线下信息 | 用户手动记录个人、门店、地址或现有链接 | V1 不引入地图检索／推荐 API，不需要定位权限来完成主路径 |
| 监控 | 云监控 + 阿里云 SLS 初选，记录错误、任务、费用和 Golden Path 事件 | 先验证关键告警与数据脱敏，不搭建复杂数据平台 |
| 部署 | 阿里云国内 ECS + Docker Compose 初选；API／worker 独立进程，RDS／OSS 托管 | 小规模内测可同机运行 API 和 worker；不视为高可用架构；App 分发按首批设备验证 |

候选能力依据：[Fastify](https://fastify.dev/docs/latest/)、[AI SDK ToolLoopAgent](https://ai-sdk.dev/docs/reference/ai-sdk-core/tool-loop-agent)、[AI SDK 兼容 Provider 适配](https://ai-sdk.dev/providers/openai-compatible-providers)、[pg-boss](https://github.com/timgit/pg-boss)、[Better Auth Expo 集成](https://better-auth.com/docs/integrations/expo)。这些文档支持能力判断，不证明 HairMate 组合已经联调通过；兼容 OpenAI 接口不意味着调用 OpenAI 服务，也不意味着所有高级接口特性都兼容。

部署与素材能力依据：[ECS 上使用 Docker Compose](https://help.aliyun.com/zh/ecs/user-guide/install-and-use-docker)、[RDS PostgreSQL](https://help.aliyun.com/zh/rds/apsaradb-rds-for-postgresql/what-is-apsaradb-rds-for-postgresql)、[OSS 私有访问权限](https://help.aliyun.com/zh/oss/user-guide/oss-bucket-acl)、[OSS 临时签名访问](https://help.aliyun.com/zh/oss/user-guide/how-to-obtain-the-url-of-a-single-object-or-the-urls-of-multiple-objects/)、[SLS 日志与告警](https://help.aliyun.com/zh/sls/)。具体实例规格、地域、预算和账号权限在部署设计中确认，不在本次文档操作中开通服务。

### 11.3 中国大陆优先：服务组合与模型评测

**已确认首批用户以中国大陆访问为主。** 推荐先用国内组合跑通主路径，不将海外模型、认证或托管服务作为国内 V1 的必需运行依赖；不因此宣称所有网络和账号条件已经验证。

| 使用条件 | 可评估组合 | 关键验证 |
| --- | --- | --- |
| 中国大陆为主（当前已确认条件） | 国内 ECS + RDS PostgreSQL + OSS + Better Auth；百炼北京地域的视觉理解及图片编辑 | 从真实设备和目标网络验证登录、上传、生成、结果下载与回访 |
| 未来主要服务海外受支持地区 | 可重新评估 Render + Supabase，以及 OpenAI／Gemini 模型 | 仅作未来替代路线；重新确认支持地区、账号、数据用途和实际质量，不并行建设 |
| 未来需要同时覆盖两类用户 | 共用业务契约与 Provider 接口，分别验证区域组合 | 另行评估需求，不默认引入双区域同步、账号互通和全局数据系统 |

模型分工：顾问模型负责照片理解、文字推理、工具调用和结构化方案；图片编辑模型负责基于真实照片修改头发。两者可来自不同 Provider，不能假设一个模型同时具备所有能力。

建议以百炼华北 2（北京）的 **`qwen3-vl-plus-2025-12-19` + `qwen-image-edit-plus-2025-12-15`** 为首组可复现评测基线；图片编辑可用 **`qwen-image-edit-max-2026-01-16`** 做质量对照。这些是官方仍列出的评测候选，不是“最新必然最好”的判断，也未被用户批准为最终型号。参考 [顾问模型](https://help.aliyun.com/zh/model-studio/qwen3-vl-plus)、[Edit Plus](https://help.aliyun.com/zh/model-studio/qwen-image-edit-plus)、[Edit Max](https://help.aliyun.com/zh/model-studio/qwen-image-edit-max)。

接入限制必须进入技术验证：

- 顾问候选在北京地域支持视觉输入和 Function Calling；不能假设其他地域能力相同。端点、API Key 与模型地域应配套确认。
- Qwen3-VL 的 JSON Object 结构化输出需使用非思考模式，且不保证字段符合指定 Schema；它未列入严格 JSON Schema 的支持列表。应用必须验证结构及业务约束，有限修正失败输出；不能在适配器中无依据地声明支持 strict Schema。参考 [百炼结构化输出](https://help.aliyun.com/zh/model-studio/qwen-structured-output)。
- 这些图片编辑候选的 API 接受图片和文字，使用同步生成接口；HairMate 自己通过 worker 提供后台任务和状态查询，不虚构供应商的异步任务恢复能力。参考 [Qwen Image Edit API](https://help.aliyun.com/en/model-studio/qwen-image-edit-api)。
- 编辑结果链接为临时链接，官方说明有效期为 24 小时；成功后及时转存私有 OSS。供应商成功返回但产品判定不合格的图片，其再生成仍应计入预算；客户端超时也不能当作供应商确认失败。参考 [图片编辑指南](https://help.aliyun.com/zh/model-studio/qwen-image-edit-guide)。

优先比较三类结果：是否遵守人物和非发型要素约束、是否呈现方案关键要求、在授权额度内的成功率／等待时间／真实费用。使用用户授权的真实样例做基准；目前未执行付费调用或质量测试，不宣称候选已经达到 HairMate 的效果要求。具体型号、快照版本、价格、地域和接口能力在接入前复核并记录，避免将“当前别名”视为永久行为保证。

未来海外替代路线的资料：[OpenAI 图像生成与编辑](https://developers.openai.com/api/docs/guides/image-generation)、[OpenAI 支持地区](https://developers.openai.com/api/docs/supported-countries)、[Gemini 图像生成与编辑](https://ai.google.dev/gemini-api/docs/image-generation)、[Render 后台任务进程](https://render.com/docs/background-workers)。本次不实施海外组合。

### 11.4 组件边界与数据流

建议同仓库划分为 `mobile / api / worker / shared`：App 负责用户交互；API 负责身份、流程和业务接口；worker 负责耗时图片任务；shared 共享类型、校验、API 客户端及纯业务逻辑。

这些是逻辑边界，不要求拆成微服务。未来 Web 可以复用接口和纯逻辑，但不能承诺 React DOM 页面与 React Native 组件直接复用。

```text
App ──认证后的请求──> API ──校验授权／额度／版本──> PostgreSQL + 任务队列
                         │                              │
                         └──顾问模型                    └──> worker ──> 图片编辑 Provider
                                                                │
App <──状态查询与授权读取── API <──任务结果／素材引用───────────────┘
                                             │
                                        私有对象存储
```

App 关闭后，已提交的任务由服务端继续处理；重新打开时查询状态，不依赖手机后台常驻。V1 不要求完整离线同步，但应支持确认后的 Brief 本地保存或导出，以及失败后的状态恢复。

### 11.5 必须现在建立的工程底线

- **权限与密钥**：Provider 密钥只留在服务端；原生会话使用适当的安全存储，验证刷新与登录回调；客户端不得自行决定业务权限。参考 [Expo SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/)。
- **任务与额度**：创建任务时校验用户、输入素材、方案版本及授权，预留额度并保证业务幂等；重试也纳入费用上限，达到上限停止。启用会产生 Provider 成本的真实生成任务前，包括样例测试和免费内测，先配置额度、停止条件与等待预期并向使用者说明，再根据测量结果调整；这不意味着 V1 向用户收费。
- **不明状态处理**：外部请求超时不等于未执行；可查询 Provider 任务时先查状态，不能查询时保留待核实状态并限制重发。队列可靠性不等于第三方调用绝不会重复计费。
- **结果保管**：临时 Provider 下载地址不是长期素材库；及时转存至私有 OSS，通过授权访问。RDS 数据库与 OSS 图片的备份、删除及恢复分别验证，不能用数据库已备份代替素材恢复测试。
- **输入与隐私**：只申请当前功能所需的照片权限；验证类型和大小；日志不记录原图、完整私密对话、访问令牌或带权限的素材链接。访问私有素材使用授权机制，详见第 11.2 节的 OSS 权限与签名访问资料。
- **可观测与测试**：记录任务耗时、结果、失败类别、重试、模型和模板版本、使用量及费用；以固定授权样例回归推荐和图片质量，覆盖权限、版本、额度、重试与 Golden Path 的确定性测试。

暂不引入：多 Agent 编排、多数据库、独立向量数据库、复杂检索平台、Kubernetes、完整微服务体系、双区域同步、实时通信平台或商家系统。只有明确需求和测量结果说明必要时再增加。

## 12. 落地顺序、风险与开放决策

### 推荐验证顺序

这不是已批准的代码实施计划，而是进入实施设计时的优先级依据：

1. **先核实最大风险**：在目标用户设备与服务地区，使用授权样例测试照片理解、基准编辑和 Brief 可读性；记录成本与失败类型。
2. **再打通最小真实历程**：App、API、任务、版本与素材访问形成完整链路，由发起人完成真实理发和首次自行打理反馈。
3. **再开展五人试点**：按第 10 节固定口径观察，修正主要阻碍；不能用新增大量功能替代问题定位。
4. **再决定其他扩展**：根据证据评估更多设备／Web 入口；理发师匹配另需数据质量、样本量和用途授权判断。

真实生活照片模拟的需求细化可以并行开展；是否纳入某次发布由具体规格与用户确认决定，不固定在五人试点之后，也不影响当前 Golden Path 验收。

### 关键风险与处理

| 风险 | V1 的处理 |
| --- | --- |
| 模拟图漂亮，但人物／发型不一致 | 明确编辑约束，样例评测与人工质量检查，拒绝不合格图，不把示意当保证 |
| 从照片误判实际头发条件 | 保存来源与不确定性，追问关键条件，Brief 留现场核实项 |
| Brief 清楚但理发师无法执行 | 现场确认与调整，保留实际执行差异；V1 不虚称能识别可靠理发师 |
| 方案修改后材料错配 | 明确版本引用和旧版标识，禁止静默覆盖 |
| 跨天流失，无法知道日常效果 | 支持续接历程与回访；分别报告完成、满意与缺失原因 |
| 模型费用与失败不可控 | 预先授权额度、有限重试、真实用量记录、超时状态核实 |
| 照片用途或分享超出用户预期 | 私有默认、目的限定、主动分享、可删除；外部导出副本能力边界说明 |

### 开放决策及影响边界

| 决策 | 当前状态 | 何时必须明确／未明确时的约束 |
| --- | --- | --- |
| 首批内测设备平台 | 未选择 | 分发真实设备构建前明确；不承诺双端同步正式上架 |
| 真实生活照片模拟细节 | 用户明确要求后续细化 | 纳入具体发布前单独确认输入、模板、交互、额度与验收；不进入当前强制路径 |
| 国内模型与云服务具体型号／供应商 | 国内组合与模型评测基线已推荐，无付费联调或效果验证 | 在已确认的大陆优先条件下，基于账号、预算与样例测试锁定；不默认批准采购 |
| 登录方式 | 内测初选邮箱／密码，尚未最终确认 | 真实用户登录前确认方式与找回路径；不因大陆优先而自动引入短信或微信集成 |
| 模拟额度、耗时与费用阈值 | 尚无测量结果，不编造数值承诺 | 启用产生 Provider 成本的真实任务前设定硬上限、展示及停止条件；免费内测同样适用 |

上述开放项不阻止本版产品范围和 App 方向成立，但文档不能被解释为所有生产配置或生活场景功能已经确定。
